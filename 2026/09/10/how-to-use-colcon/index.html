如何优雅的使用"colcon & ament_cmake"构建一个C++工程

0. 前言

依据笔者之前的开发经验,每次开发完一个新功能包就开始头疼如何写cmake,LLM写的CMake又很容易报错,依赖agent更是会导致生成的cmake不像人样,甚至可能原本建立好的架构都会被agent无情拆分.

在”colcon & ament_cmake”这套c++包管理工具如此难用的同时,官方文档的维护亦不尽人意,colcon文档并未详细给出库的导出原则,ament_cmake/ament_cmake_auto更是甩手掌柜,只有源代码仓库里面的一大堆cmake宏可以看.

所以本博客旨在探索出一个使用”colcon & ament_cmake”构建C++工程时的通用cmake模板

注: 本博客不讲解最基本的ROS工作空间相关的概念

读者在实际使用的时候可以尝试直接将本博客复制给agent,保证生成代码的规范性

2. 一个优雅的C++工程架构

针对这个话题,C++开发者们众说纷纭,各执己见,这里笔者认为在”colcon & ament_cmake”这套c++包管理工具构建的工程下比较好的架构

  • assets: 静态资源,存储图片,文档等,也可以存储一些传感器内外参,模型文件等很快调整好且长时间不会变的参数,一般的科研软件包主要是存储介绍论文的动图等
  • autostart: 看你的项目需不需要自动启动
  • build,install,log: 都是colcon自动生成的,这里不用一般c++工程中常用的bin文件夹来存储二进制文件,最主要的原因是ros2 run命令也不会费力到哪里去
  • scripts: 存储脚本文件,包括但不限于各种*.sh文件,可用于程序启动,git维护,编译等多个功能
  • src: source code的简称,存放源代码

注: 至于对软件版本要求严格的项目,读者可以自行添加cmake文件夹来存放*.cmake文件以及3rdparty来存储固定版本的第三方软件

4. 模板逐段拆解

模板能直接抄,但抄的时候不知道自己抄了什么,下次改需求还是会卡。这一节把模板拆成若干块,每块讲清楚为什么这么写以及换个写法会怎样

4.1 地基:版本、包名与编译选项

  • cmake_minimum_required(VERSION 3.8):ament_cmake的宏最低要求3.8,低于它install(EXPORT)的默认策略与ament的假设不一致。写更高版本(比如3.16)也没问题,Ubuntu 22.04(Humble官方环境)自带CMake 3.22
  • project(detection):这个名字必须和package.xml里的<name>一字不差。它决定了${PROJECT_NAME}、安装目录share/detection以及ament索引里的包名;不一致的典型症状是ros2 run找不到包、ament_index_cpp查不到share目录
  • add_compile_options是目录级的,本目录及子目录下所有目标都会带上;只想给某一个目标加,用target_compile_options(<target> PRIVATE -Wall)
  • if(NOT CMAKE_CXX_STANDARD)先判空,是为了让命令行的-DCMAKE_CXX_STANDARD=20能覆盖模板里的默认值;直接set(CMAKE_CXX_STANDARD 17)会把命令行传进来的值顶掉,临时试C++20特性的时候会很难受
  • CMAKE_CXX_STANDARD_REQUIRED ON表示”编译器不支持这个标准就直接报错”,而不是悄悄降级到旧标准去编。Humble官方包统一是C++17

4.2 依赖:三类find_package,以及和package.xml的分工

模板里那几行find_package其实分成三类,每一类在package.xml里的对应写法都不一样:

类型 CMake侧 package.xml侧 例
构建系统 find_package(ament_cmake REQUIRED) <buildtool_depend>ament_cmake</buildtool_depend> 每个包都要
上游功能包 find_package(driver REQUIRED) <depend>driver</depend> driver、common_libs
第三方库 find_package(OpenCV REQUIRED) <depend>libopencv-dev</depend> OpenCV、Eigen、yaml-cpp
标准库设施 find_package(Threads REQUIRED) 一般不写 Threads::Threads

两边的分工要分清:

  • package.xml是给colcon和rosdep看的:colcon靠它排构建顺序(先编driver再编detection),rosdep install --from-paths src --ignore-src -r -y靠它装系统依赖,这里的名字是rosdep key
  • find_package是给CMake看的:它才决定编译期能拿到哪些头文件路径和库,这里的名字是CMake包名

rosdep key和CMake包名经常不是一回事,这是新手最容易漏的一环。实测:

所以显式风格里两处都得写。而ament_cmake_auto的自动find_package只对”rosdep key恰好等于CMake包名”的包有效(rclcpp、sensor_msgs、ament_index_cpp这类ROS包基本都符合),OpenCV这种必须自己手写

REQUIRED建议都加上:依赖找不到就该在配置阶段停下来,而不是留到链接期报一堆undefined reference;真正可选的依赖才用QUIET并自己判_FOUND

依赖的书写顺序建议固定为:构建系统 → 上游功能包 → 第三方 → 标准库,模板里就是这个顺序

4.3 生成目标:库与可执行

显式风格就是标准CMake:

几个容易踩的点:

  • 不写SHARED/STATIC时默认是STATIC(BUILD_SHARED_LIBS没打开的话),要动态库就明确写SHARED
  • 源文件建议一个个列出来,不要file(GLOB):glob的结果在configure阶段就定死了,新增.cpp不会触发重新配置,现象就是”文件明明加了却没编进去”。ament_auto_add_library的DIRECTORY参数内部也是file(GLOB_RECURSE),同样有这个毛病
  • PIC:SHARED/MODULE目标CMake默认就开POSITION_INDEPENDENT_CODE;STATIC目标默认不开,而这个静态库一旦被链接进别人的.so,就会报relocation R_X86_64_PC32 ... can not be used when making a shared object。模板里那句set_target_properties(... POSITION_INDEPENDENT_CODE ON)就是为这种情况准备的,一般不亏

然后是每个库都要写的两段:头文件接口和依赖接口

PUBLIC表示”我自己要用,链接我的下游也要用”,所以必须写成生成器表达式,把”编译期用源码树路径”和”安装后用<prefix>/include“分开。只写裸路径${CMAKE_CURRENT_SOURCE_DIR}/include的话,一旦后面要install(EXPORT)导出这个目标,CMake直接报错(详见§5.6坑1)

这里的PUBLIC是”我用了,而且这个依赖出现在我的公开头文件里,下游要一起继承”。写成PUBLIC之后,下游只要链接detection_core,就自动拿到了UsbCam、common_libs和OpenCV,不用重复写一遍。判断标准很简单:公开头文件里#include了谁的类就写PUBLIC;只在.cpp里用到的写PRIVATE(日志、内部实现的算法库都是这类)

同一个目标上,target_link_libraries要么全用关键字形式(PUBLIC/PRIVATE/INTERFACE),要么全用不带关键字的老形式,混着写一定报错,实测报错原文:

4.4 引用别人的库:三种写法

这块是”能编过”和”编对”的分水岭。下游引用上游提供的库,一共三种写法

写法一:现代namespaced目标(推荐)

driver::UsbCam是一个IMPORTED目标,由上游的install(TARGETS ... EXPORT ...)+ament_export_targets生成。它的好处是自带头文件路径、编译定义和传递依赖,你不需要知道上游的头文件装在哪、它还依赖谁。命名空间默认是<包名>::,所以上游包叫driver、库目标叫UsbCam,你这边写的就是driver::UsbCam

写法二:ROS传统宏ament_target_dependencies

它做的事是把这些ROS包的include路径、库、编译定义一次性挂到目标上。三条规则要记住:

  1. 参数里的包必须已经find_package过,否则直接FATAL_ERROR:the passed package name 'xxx' was not found before
  2. 关键字只能写在包名前面:ament_target_dependencies(my_node SYSTEM rclcpp);写成ament_target_dependencies(my_node rclcpp SYSTEM)会报SYSTEM keyword is only allowed before the package names
  3. 它内部用的是不带关键字的target_link_libraries,所以同一个目标上不要再写关键字版(就是§4.3里那个all-keyword or all-plain报错)。传统写法与现代写法二选一,不要混

另外一个细节:现代ROS包同时提供${pkg}_TARGETS(导入目标)和${pkg}_LIBRARIES(旧的绝对路径列表),ament_target_dependencies会优先用${pkg}_TARGETS,只有在对方没导出目标时才回退到旧变量。这就是为什么有些包写ament_target_dependencies就够了,而有些老包还是得靠${pkg}_LIBRARIES

写法三:旧式变量

只有当上游只做了ament_export_libraries(没导出namespaced目标)时才需要这么写。${pkg}_LIBRARIES是一串绝对路径,拿不到传递依赖和编译定义,信息量比写法一少一大截。ament_cmake_auto的ament_auto_package()默认就走这条路(见§5.4)

注:第三方库(OpenCV/Eigen/yaml-cpp/CUDA/Threads)建议一律用target_link_libraries引用:${OpenCV_LIBS}、Eigen3::Eigen、yaml-cpp、CUDA::cudart、Threads::Threads。ament_target_dependencies走的是${pkg}_INCLUDE_DIRS/${pkg}_LIBRARIES这套约定,能不能用完全取决于对方提供了什么变量:OpenCV恰好两套都有(OpenCV_INCLUDE_DIRS+OpenCV_LIBRARIES)所以能work,而Eigen3只提供了EIGEN3_INCLUDE_DIRS(全大写,对不上Eigen3_INCLUDE_DIRS)和导入目标Eigen3::Eigen,用ament_target_dependencies(t Eigen3)会静默地什么都不链接,然后你在编译期愉快地收获”找不到Eigen/Core”。不确定的时候用target_link_libraries最不容易出错

4.5 安装:装到哪ros2 run才找得到

  • ARCHIVE=静态库(.a),LIBRARY=动态库(.so),RUNTIME=可执行文件(以及Windows下的.dll)。三个都写一遍是最省事的写法,哪怕现在只产出动态库
  • 可执行装到lib/${PROJECT_NAME}/而不是bin/,是因为ros2 run <pkg> <exe>就是按这个路径去找的;想让可执行进PATH,把RUNTIME DESTINATION改成bin即可
  • EXPORT ${PROJECT_NAME}_export把这两个目标登记进一个”导出集合”,等会ament_export_targets才会把它写进share/<pkg>/cmake/。少了这一步,下游find_package(detection)能成功,但拿不到detection::detection_core——这是最常见的”导出了个寂寞”

资源文件按同样的思路装:

  • 目录后面的斜杠很关键:config/表示”把config里面的内容装过去”(得到share/detection/config/cameras.yaml);写成config(不带斜杠)会得到share/detection/config/config/cameras.yaml
  • 头文件、config、launch、rviz配置这些运行时资源,统一装到share/${PROJECT_NAME}/下面;代码里用ament_index_cpp::get_package_share_directory("detection")取路径,不要拼绝对路径(换机器、换安装前缀都会崩)。模板里find_package(ament_index_cpp REQUIRED)就是为了这个,它导出的是现代目标,链接ament_index_cpp::ament_index_cpp即可
产物 写法 落地路径
动态库 LIBRARY DESTINATION lib install/<pkg>/lib/libdetection_core.so
静态库 ARCHIVE DESTINATION lib install/<pkg>/lib/libX.a
可执行(ros2 run用) RUNTIME DESTINATION lib/${PROJECT_NAME} install/<pkg>/lib/<pkg>/usb_camera_demo
可执行(进PATH) RUNTIME DESTINATION bin install/<pkg>/bin/<exe>
头文件 install(DIRECTORY include/ DESTINATION include) install/<pkg>/include/<pkg>/*.hpp
参数/配置 share/${PROJECT_NAME}/config install/<pkg>/share/<pkg>/config/*.yaml
launch share/${PROJECT_NAME}/launch install/<pkg>/share/<pkg>/launch/*.py

注:--symlink-install时这些安装出来的文件是指向源码树的软链接,所以改*.yaml不用重编,这也是§1里那条命令最大的价值

4.6 导出:让下游能用你

导出只有三行,但决定了别人find_package你之后能拿到什么:

  • ament_export_targets(<export名> HAS_LIBRARY_TARGET):把install(TARGETS ... EXPORT <export名>)登记的集合装成share/<pkg>/cmake/<export名>Export.cmake,并自动加上<pkg>::命名空间。HAS_LIBRARY_TARGET告诉ament”这里面有真的库文件”,它会额外注册环境钩子,让非merged安装下的lib目录进运行期搜索路径
  • ament_export_include_directories(include):让下游的<pkg>_INCLUDE_DIRS里有你的头文件目录。注意这里的目录要和install的一致:install(DIRECTORY include/ DESTINATION include)对应include
  • ament_export_dependencies(...):传递依赖,这是最容易漏的一行。你的公开头文件里#include "driver/usb_cam.hpp",下游编译时也需要driver的头文件;不写这行,下游会直接报”找不到driver/usb_cam.hpp“,或者报找不到OpenCV的头。原则是:公开头文件里出现过的依赖,都要在这里导出

4.8 收尾:ament_package()

ament_package()负责生成<pkg>Config.cmake、<pkg>Config-version.cmake、环境脚本(local_setup.sh等)以及ament索引里那条包记录。它必须是最后一行,而且所有的ament_export_*都要在它之前调用(否则报must be called before ament_package())

注:用ament_cmake_auto时这一步由ament_auto_package()代劳,不要再手写ament_package(),否则会重复生成

5. ament_cmake与ament_cmake_auto:同一条命令的两种写法

5.1 两者的关系

ament_cmake_auto不是一个平行的构建系统,它只是ament_cmake上面的一层宏:ament_auto_*这些宏内部仍然是add_library/target_link_libraries/install/ament_target_dependencies。理解这一点,后面所有差异都好解释:

  • 显式风格要写的东西,auto风格一个都没少,只是被宏藏起来了
  • auto风格随时可以”手动介入”,直接写原生CMake命令
  • 用哪套风格由package.xml的<buildtool_depend>决定:ament_cmake还是ament_cmake_auto

5.2 生成目标

要做的事 显式(ament_cmake) 自动(ament_cmake_auto)
建库 add_library(detection_core SHARED src/a.cpp) ament_auto_add_library(detection_core SHARED src/a.cpp)
建可执行 add_executable(demo src/demo.cpp) ament_auto_add_executable(demo src/demo.cpp)
靠目录扫源文件 自己file(GLOB)(不推荐) ament_auto_add_library(x SHARED DIRECTORY src)
加头文件目录 target_include_directories(x PUBLIC $<BUILD_INTERFACE:...> $<INSTALL_INTERFACE:include>) 宏自动加,但加的是源码树裸路径(坑1)
链接本包内其它库 手写target_link_libraries(x PUBLIC other) 宏自动链接${PROJECT_NAME}_LIBRARIES里已有的库
链接上游依赖 手写target_link_libraries或ament_target_dependencies 宏内部ament_target_dependencies(x SYSTEM <已找到的build依赖>)
登记目标 不需要 自动追加到${PROJECT_NAME}_LIBRARIES/${PROJECT_NAME}_EXECUTABLES

ament_auto_add_library/ament_auto_add_executable内部一共做四件事:

  1. 如果包里有include/目录,target_include_directories(<target> PUBLIC <源码树绝对路径>)
  2. 链接本包先前建好的库(可以用NO_TARGET_LINK_LIBRARIES关掉)
  3. ament_target_dependencies(<target> SYSTEM <所有已找到的build依赖>)——注意这个SYSTEM,意思是上游头文件目录以-isystem传入,它们的警告不会算到你头上
  4. 把目标记进${PROJECT_NAME}_LIBRARIES/${PROJECT_NAME}_EXECUTABLES,交给ament_auto_package()统一安装

宏不做的两件事:不管PIC、不管安装规则。所以set_target_properties(... POSITION_INDEPENDENT_CODE ON)该写还得写(静态库尤其),安装交给ament_auto_package()

顺带一提,这两个宏都有DIRECTORY参数给你省事:

但是上面说过,它也是configure期的glob,新增文件不会被感知;要稳定的行为还是老实列文件

判据是”宏内部到底有没有发出带实参的非关键字调用”:如果package.xml里没有任何能提供${pkg}_TARGETS/${pkg}_LIBRARIES的依赖(比如纯C++的基础库包),宏的调用是空实参,不会锁定签名,关键字形式依然能写;但只要有一个rclcpp、sensor_msgs这样的依赖被找到,签名就被锁成”非关键字”了。与其记这条规则,不如记结论:auto风格里给目标补库,就跟宏保持同一种风格(不带关键字);要么干脆别在auto包里手动链接,把活留给package.xml

5.4 导出库:两种风格的差别最大

想给下游什么 显式风格 auto风格
头文件 install(DIRECTORY include/ DESTINATION include)+ament_export_include_directories(include) ament_auto_package()自动(有include/就装、就导出)
库:现代namespaced目标<pkg>::<target> install(TARGETS t EXPORT <pkg>_export ...)+ament_export_targets(<pkg>_export HAS_LIBRARY_TARGET) 默认没有,必须自己补这两句
库:旧式变量${pkg}_LIBRARIES ament_export_libraries(t) ament_auto_package()默认走这条
传递依赖 ament_export_dependencies(...) ament_auto_package()只导出”既是build依赖又是run依赖”的包
安装规则 全手写 ament_auto_package()自动

也就是说:ament_auto_package()导出的是旧式的${pkg}_LIBRARIES(绝对路径列表),不是现代目标。下游能用ament_target_dependencies或者target_link_libraries(x ${pkg_LIBRARIES}),但拿不到pkg::target。想要现代目标,就在auto包里自己补上(库的安装规则仍由ament_auto_package()负责,重复装到同一路径无害):

宏 作用 备注
ament_auto_find_build_dependencies([REQUIRED pkg...]) 按package.xml找所有build/buildtool依赖 REQUIRED列表里的包必须已在package.xml,否则FATAL_ERROR
ament_auto_find_test_dependencies() 按<test_depend>找测试依赖 不带参数

ament_auto_package()的三个常用参数:

参数 作用
INSTALL_TO_SHARE config launch 把config/、launch/装到share/<pkg>/
INSTALL_TO_PATH 可执行装到bin/(默认lib/<pkg>/,ros2 run用默认的)
USE_SCOPED_HEADER_INSTALL_DIR 头文件装到include/<pkg>/而不是include/

注:构建时可能看到这句提示(不是错误):

这是提醒你Kilted起默认行为会变成scoped安装。如果你的头文件本来就写成include/<pkg>/xxx.hpp(推荐这么写),保持默认即可;真按提示打开USE_SCOPED_HEADER_INSTALL_DIR反而会变成include/<pkg>/<pkg>/xxx.hpp,#include路径也得跟着改

5.6 auto风格的三个坑

坑1:ament_auto_add_library把源码树裸路径写进接口,导致install(EXPORT)报错

宏加头文件目录时用的是${CMAKE_CURRENT_SOURCE_DIR}/include这种绝对路径,而install(EXPORT)不允许导出源码树路径。实测报错:

两种修法:要么不做install(EXPORT)(也就别指望现代导出了,下游只能用${pkg}_LIBRARIES);要么按§5.5的③把接口改写成$<BUILD_INTERFACE:...>/$<INSTALL_INTERFACE:include>。既然推荐导出namespaced目标,就老老实实改

坑2:ament_auto_find_build_dependencies()只认package.xml

它是遍历package.xml里的依赖去find_package,所以:

  • 传REQUIRED列表时,列表里的包**必须已经写在package.xml**里,否则直接FATAL_ERROR
  • 依赖写漏了不会有任何提示,只会在编译/链接期以”找不到头文件”的形式暴露
  • <depend>libopencv-dev</depend>这种rosdep key是find_package不到的(§4.2实测),第三方库仍然要自己find_package+链接

坑3:安装和收尾不能重复

  • 用了ament_auto_package()就不要再手写install(TARGETS ...)装库、也不要再写ament_package()。唯一例外是§5.4里为了现代导出而额外补的那段install(TARGETS ... EXPORT),它只登记EXPORT,路径和auto的一致
  • ament_auto_package()导出的是”既是build依赖又是run依赖”的包;如果某个公开头文件依赖的包在package.xml里只写成<build_depend>,它不会被导出,下游会缺头文件——这种情况自己补一句ament_export_dependencies(...)

5.7 到底该选哪个

情况 建议
纯算法库/工具库,依赖简单,只有一个库目标 ament_cmake_auto,省事
要引用第三方库(OpenCV/Eigen/CUDA…) ament_cmake,显式写更清楚,也不受§5.3签名限制
要导出给下游、会被别的包target_link_libraries ament_cmake更直接(auto也能做,但要额外补两段)
一个包里有多个库、需要精细控制PUBLIC/PRIVATE ament_cmake
包很多、结构高度一致、想用同一套模板 ament_cmake_auto

不管选哪个,同一个仓库里要有统一规矩,比如”基础库用auto,涉及第三方依赖或导出的包用显式”,别今天一个风格明天一个风格。显式风格最大的优点是报错好定位:出问题时你看到的每一行都是自己写的

6. 推荐的功能包设计模式

前面讲的都是”怎么写能编过”,这一节讲”怎么划分才能不用天天改CMake”。这套模式本质上就是一句话:让每个包的CMake都短到能一眼看完

6.1 一个包只干一件事,依赖链单向

工程里最舒服的划分是按”职责层次”分包,每一层只依赖它下面的层:

  • common_libs:纯C++工具库(数学、字符串、时间),不依赖ROS,谁都能用
  • driver:硬件驱动库,输出libUsbCam.so,只依赖OpenCV这类第三方,不掺业务逻辑
  • detection:业务算法包,链接上面两个,输出”核心库+示例可执行”

这样分的好处很直接:改驱动不会触发算法重编(只重新链接),单测算法不需要硬件,换相机只动驱动包。反过来,一个包里既有相机驱动又有卡尔曼滤波还有ROS节点,那动一行滤波代码就要重编整个包,而且没法单独测

依赖绝对不要成环。colcon按package.xml做拓扑排序,显式成环会直接报Circular dependency;而”靠CMake侥幸编过”的隐性环,表现为全量构建时随机失败,非常难查

6.2 核心库与节点分离

同一个业务包里,建议再分两层:

  • 核心库不依赖rclcpp(头文件里不出现#include <rclcpp/rclcpp.hpp>):可以脱离ROS环境编译、可以写不需要rclcpp::init的单元测试、可以被其它不带ROS的工程复用
  • 节点层要薄:只做参数声明、话题收发、把数据递给核心库,不写算法
  • 代价只是多一个add_library+add_executable,收益是”算法可测、可复用、编译快”

以后加了节点,package.xml里补<depend>rclcpp</depend>,CMake里find_package(rclcpp REQUIRED)并target_link_libraries(detection_node detection_core rclcpp::rclcpp)即可,核心库一行都不用改

6.3 头文件、库名与命名空间

  • 头文件统一放include/<pkg>/xxx.hpp,install到include/(不打开USE_SCOPED_HEADER_INSTALL_DIR),于是#include "detection/camera_grabber.hpp"在源码树里和安装后都成立;每个包的头文件都有自己的目录前缀,合并安装时不会互相污染
  • 库目标名要和包名有明显关联(detection_core、UsbCam),导出后的命名空间是包名(detection::detection_core、driver::UsbCam),下游一眼就能看出这个库是从哪来的
  • C++侧再套一层自己的命名空间(比如gugauav::detection)是锦上添花,能避免和别人的CameraGrabber撞名

6.4 参数与资源:一律进share/,代码里用ament index取

  • 可调参数不要写死在代码里,也不要编译进二进制:config/*.yaml装到share/<pkg>/config/,launch/*.py装到share/<pkg>/launch/
  • 代码里用ament_index_cpp::get_package_share_directory("<pkg>")取路径;源码树路径只在”没安装直接跑”时当兜底,可以用target_compile_definitions编进目标
  • --symlink-install下这些文件是软链接,改完yaml不用重编,调参体验会好很多
  • 传感器内外参、模型文件这类”很大又很久不变”的资源,可以放工程的assets/,由scripts/拷贝或由launch引用,不要塞进功能包

6.5 测试:单测不要硬件

  • 每个库配一个gtest,ament_add_gtest注册,target_link_libraries只链被测的那个库
  • 涉及硬件的部分(相机、串口)不要进单测,把”解析配置””未打开设备时的行为”这类纯逻辑抽出来测;真机验证交给scripts/里的脚本
  • 测试数据路径用target_compile_definitions编进目标,不要在测试代码里写相对路径

6.6 自查清单

写完一个包,过一遍这几条基本不会出大问题:

  1. project()的名字和package.xml的<name>一致吗?
  2. package.xml里的<depend>覆盖了所有find_package的上游包吗?(colcon靠它排顺序)
  3. 第三方库的rosdep key写了吗?(是libopencv-dev,不是OpenCV)
  4. 每个库都开PIC了吗?(静态库尤其要注意)
  5. 公开头文件用到的依赖都用PUBLIC链接、并且在ament_export_dependencies里导出了吗?
  6. 要导出的库,install(TARGETS ... EXPORT ...)和ament_export_targets(...)是不是成对出现了?
  7. 可执行装到lib/${PROJECT_NAME}了吗?(ros2 run找不找得到)
  8. 用了ament_auto_package()的话,有没有重复写install/ament_package()?
  9. lint排除项用的是AMENT_LINT_AUTO_EXCLUDE吗?
  10. 构建完ldd看一眼下游库,运行期依赖真的挂上了吗?

7. 报错速查

报错/现象 原因 修法
Target "x" INTERFACE_INCLUDE_DIRECTORIES property contains path ... which is prefixed in the source directory ament_auto_add_library把源码树裸路径放进了接口,同时又install(EXPORT) 改写成$<BUILD_INTERFACE:...>/$<INSTALL_INTERFACE:include>,或不做现代导出(坑1)
ament_auto_find_build_dependencies() called with required packages that are not listed as a build/buildtool dependency in the package.xml auto只认package.xml 往package.xml补<depend>,或去掉REQUIRED列表
must be either all-keyword or all-plain 同一目标上关键字与非关键字target_link_libraries混用(可能来自ament_target_dependencies或auto宏) 统一成一种;auto包里补库时用不带关键字的形式
ament_target_dependencies() the passed package name 'x' was not found before 没先find_package 补find_package(x REQUIRED)
ament_target_dependencies() SYSTEM keyword is only allowed before the package names 关键字写到包名后面了 改成ament_target_dependencies(t SYSTEM pkg)
下游find_package(driver)成功但没有driver::UsbCam 上游没登记EXPORT,或没调ament_export_targets 上游补install(TARGETS ... EXPORT ...)+ament_export_targets(... HAS_LIBRARY_TARGET)
下游编译报”找不到上游头文件里的依赖”(比如OpenCV头) 上游漏了ament_export_dependencies(OpenCV) 补上,package.xml也要有对应的<depend>
ament_package()没被调用/被调用了两次 用了ament_auto_package()又手写ament_package() 二选一
error while loading shared libraries: libUsbCam.so: cannot open shared object file 运行期没source install/setup.bash,或上游没装库 source install/setup.bash;用ldd定位
ros2 run <pkg> <exe>找不到可执行 RUNTIME DESTINATION不是lib/${PROJECT_NAME} 按§4.5改安装路径
relocation R_X86_64_PC32 ... can not be used when making a shared object 目标没开PIC set_target_properties(t PROPERTIES POSITION_INDEPENDENT_CODE ON)
copyright/cpplint用例莫名出现并失败 包模板里的set(ament_cmake_copyright_FOUND TRUE)在Humble不可靠 改用set(AMENT_LINT_AUTO_EXCLUDE ament_cmake_copyright ament_cmake_cpplint)
单包能编,全量colcon build顺序错乱 package.xml缺依赖,colcon排不出拓扑 依赖写全,rosdep install --from-paths src --ignore-src -r -y
